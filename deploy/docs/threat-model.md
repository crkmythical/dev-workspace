# Threat Model

## Adversary Classes

| Adversary | Capability | Mitigations |
|-----------|-----------|-------------|
| **Network observer** | Inspect traffic on local/ISP network | Traffic from the workspace goes through Clash, encrypted to the proxy node, and the egress firewall (on by default) drops what tries to leave any other way; the tunnel uses TLS |
| **Host compromise** | Read host filesystem, Docker volumes | Vault content is encrypted at rest (gocryptfs, scrypt N=2^18 for new vaults); the ciphertext directory is root-only. The passphrase is NOT memory-only (see Non-Guarantees): whoever can read the container's filesystem as root, its environment or its logs can unlock it |
| **Code running in the workspace** (a malicious package, a stolen code-server session, a rogue extension) | Everything the `dev` user can do | Runs as the unprivileged user `dev` with no capabilities, a clean environment (none of the workspace's secrets) and no setuid binary but `doas`, which opens a short list of commands (see Privilege Separation). It cannot read the master password, the backup or subscription credentials, the session key, the audit log or the ciphertext, cannot reconfigure the gate or the egress firewall, and cannot connect out except through Clash |
| **Container escape** | Break out of Docker isolation | Not privileged, but `CAP_SYS_ADMIN` (FUSE) and `seccomp:unconfined` (the desktop's bwrap sandbox) weaken isolation; on Linux hosts with AppArmor the opt-in `docker-compose.apparmor.yml` also drops the AppArmor profile (see Non-Guarantees). Treat the container as a moderate boundary; use a dedicated VM for stronger separation |
| **GitHub breach** | Access vault repository contents | Repository contains only gocryptfs ciphertext; AES-256. It also holds `gocryptfs.conf`, the passphrase-wrapped master key, so a weak passphrase can be guessed offline: new vaults wrap it with scrypt N=2^18, four times the work per guess of gocryptfs's default |
| **Sync wire observer** | Intercept sync traffic | AES-256-GCM AEAD + PNG camouflage; no plaintext metadata. The key is PBKDF2-HMAC-SHA256-stretched from the passphrase, so a captured envelope cannot be brute-forced at raw-hash speed |
| **Physical access** | Access to powered-off machine | Vault locked on container stop; workspace content is not on disk in the clear. The credentials listed under Non-Guarantees are |
| **Cloudflare compromise** | Access tunnel traffic | End-to-end encryption between browser and container; CF sees TLS only |

## Trust Boundaries

1. **Passphrase → vault**: the passphrase (typed, or `PASSWORD`) is handed to gocryptfs; in the browser the sync key derived from it (PBKDF2-HMAC-SHA256, password-stretched) is a non-extractable CryptoKey. See Non-Guarantees for where the passphrase also lives
2. **Container → Host**: Docker isolation; single mapped port (localhost only)
3. **Container → Internet**: through Clash only. `http_proxy` and friends point at it, `ssh` is configured to use it, and an nftables default-DROP filter lets nothing else out except the networks the operator lists in `EGRESS_ALLOW_CIDRS` (see Egress)
4. **Workload → root**: the `dev` user reaches root only through `doas`, which runs the generated list of `sdw` commands (`sdw doas-rules`) with a clean environment
5. **Sync SPA → Server**: AEAD-encrypted envelopes; server cannot read plaintext
6. **Vault → GitHub**: Only ciphertext pushed; git history contains no plaintext

## Privilege Separation

Everything the user runs (code-server and its terminals, the desktops and their applications, build tools, whatever a package's install script does) runs as `dev` (uid 1000), with its home inside the vault (`/workspace/home`), so shell history, tool caches and configuration are encrypted at rest and gone when the vault is locked. The services that hold the secrets or guard the perimeter keep their own identities: the gate, backup, sync and supervisord are root's, Caddy is `caddy`, Clash is `clash`.

* **No secrets in the workload's environment.** `sdw workload` starts every process with an allowlisted environment (locale, proxy variables, display, the desktop's settings). `WORKLOAD_ENV` names more variables to pass; one that is a workspace secret (`PASSWORD`, `RESTIC_*`, `AWS_*`, `CLASH_SUBSCRIPTION_URL`, `*_FILE`, ...) is refused with a warning. `75-privilege.sh` checks the running code-server's environment as well.
* **No second login.** code-server runs with `--auth none` and KasmVNC with `-DisableBasicAuth`: the session gate in front of Caddy is the only login, so no copy of the master password sits where `dev` could read it. A password the start-up generated is kept in `/var/lib/sdw/master-password` (root, 0700).
* **The vault belongs to `dev`, to `dev` alone.** It is mounted by root with `-allow_other -force_owner 1000:1000`; the mount point is 0700 and gocryptfs turns on `default_permissions`, so no other user (Caddy, Clash) can enter it. The ciphertext directories `/vault/cipher` and `/pentest/cipher` are made 0700 at every start.
* **The sync key source is not in the vault.** With `SYNC_ENABLED` the passphrase is written to `/run/sdw/sync-passphrase` (root, 0700 directory), removed by `lock-vault` and scrubbed by self-destruct.
* **No setuid or setgid file but `doas`.** The rest are stripped at build time. `dev` has no capabilities.
* **The bridge.** `doas` runs `/usr/local/libexec/sdw-priv/<verb>` as root with a clean environment, for the verbs in `PRIVILEGED_VERBS` (`core/src/workspace/workload.rs`: `doctor`, `lock-vault`, `unlock-vault`, `desktop-*`, `set-clash-dns`, `setup`, `push`, `pull`, `audit-log`, the pentest commands, `init-*`). Nothing else, no shell, no `keepenv`. A bridged process reads the container's configuration from PID 1's environment, which only root can read. `self-destruct`, `destruct-passphrase` and `backup-init` are NOT in the list: they are for the operator (`docker exec`) and print that when `dev` runs them. The rules file is generated from the same list the symlinks are, and `75-privilege.sh` checks that they agree.

What this does not give: the arguments of a bridged command are the workload's, so a bug in one of those commands is a way to root; and root in this container is still a container root with `CAP_SYS_ADMIN`.

## Residual Risks

| Risk | Likelihood | Impact | Acceptance |
|------|-----------|--------|------------|
| Memory dump while unlocked | Low | High | Mitigated: core dumps disabled, key zeroed on lock |
| gocryptfs vulnerability | Very Low | Critical | Monitor CVEs; key rotation is manual (`gocryptfs -passwd` on the cipher dir — there is no built-in command, and it desyncs the passphrase copies listed under Non-Guarantees). `gocryptfs -passwd -scryptn 18 /vault/cipher` also raises the scrypt cost of a vault created before it became the default |
| Clash subscription compromise | Medium | Medium | Traffic visible to proxy provider; use trusted provider |
| Docker Desktop vulnerability | Low | High | Keep updated; consider VM alternative |
| Browser IndexedDB key extraction | Low | Medium | Key marked non-extractable; cleared on rotation |
| A bug in a bridged `sdw` command | Low | High (root in the container) | The list is short and generated; the commands take few arguments; `dev` has no other way up |
| A tool release replaced upstream | Low | High | Every tool baked into the image is pinned with a checksum (`src/image/tools/*.env`, `make update-tools`) and verified when it is downloaded; the pins are reviewed like any dependency |

## Security Invariants

1. Workspace content is written only inside the FUSE mount. Each writer checks that the vault is mounted first (`desktop-start`, `backup-watcher`, `vault-sync`, notifications, the vault-gated steps of the boot plan, and sync uploads, which need the key that only exists while unlocked), so nothing lands in the container's own filesystem while locked. The check is per writer, not one central guard
2. The sync wire protocol reveals no file paths, names, or content in plaintext. Listing the shared directory needs proof of the sync key, and file content is never served back. An upload is committed with `openat`/`renameat` and `O_NOFOLLOW`, so a symlink planted in the shared directory cannot redirect it
3. Replay protection claims a nonce only after the envelope has authenticated, so forged requests cannot flush genuine nonces out of the bounded window
4. Container destruction leaves no recoverable traces on host (best effort; see Self-Destruct)
5. Every ingress route is behind one authentication gate, deny-by-default. Caddy runs a session-cookie `forward_auth` check in front of all routes except the login surface (`/auth/*`) and the break-glass destruct endpoint (`/sync/api/destruct`). The session cookie is required on HTTP requests AND on WebSocket upgrades alike (code-server, KasmVNC `/websockify`, Selkies `/desktop/api/websockets`) — a same-origin cookie rides the WS handshake, which Basic Auth cannot. A route added without its own auth is closed, not exposed. A WebSocket handshake whose `Origin` is another site is refused even with a valid cookie (cross-site WebSocket hijacking of the desktop or the terminal). The cookie is HMAC-signed with a random key chosen at boot, or, with `AUTH_SESSION_PERSIST`, a random key kept in `/var/lib/sdw/session.key` (root, never derived from the password, so a cookie cannot be used to guess it offline); it is `Secure` when the client's connection was HTTPS. Every response carries the baseline security headers (CSP on the gate's own pages and `/sync/`, `X-Content-Type-Options`, `Referrer-Policy`, HSTS under HTTPS). See `deploy/docs/design-unified-auth-gateway.md`
6. Nothing in the workspace leaves the container except through Clash, or to a network the operator listed. The nftables filter is loaded before Clash starts and the boot stops if it cannot be loaded; `doctor` fails if it is wanted and missing. See Egress

## Non-Guarantees

What this system does NOT promise, so nobody relies on it:

- **Egress.** The firewall is on by default (`EGRESS_ENFORCE`; only `0`, `false`, `no` or `off` turn it off, and a value that cannot be read leaves it on). It is an nftables default-DROP OUTPUT filter that lets out only loopback, replies on established connections, the `clash` uid, and the networks in `EGRESS_ALLOW_CIDRS` (addresses and blocks only; /0 and anything wider than a /8, or a /16 for IPv6, is refused and stops the boot). So a process that ignores the proxy variables, speaks UDP or QUIC, runs under `noproxy`, or resolves names itself is blocked, for root as much as for `dev`; names resolve through Clash's DNS, so a query cannot leak past it. `ssh` ignores the proxy variables, so the boot writes `/etc/ssh/ssh_config.d/10-sdw-egress.conf` to send it through Clash (the user's `~/.ssh/config` wins for a host given `ProxyCommand none`). What it does not stop: the container holds `CAP_NET_ADMIN`, so a root process (not `dev`, which has no capability and no bridged command that touches nft) can delete the table; traffic to an allowed network leaves with the host's real address; and a destination reached through Clash is only as private as the proxy node. With `EGRESS_ENFORCE=0` only the proxy variables point at Clash, and the boot and `doctor` say so. The pentest plugin's tools that open raw sockets, and a scan of a network that is not allowed, need the network listed in `EGRESS_ALLOW_CIDRS` or the firewall off; Tor is configured to reach the network through Clash, so it should work behind the firewall (not run with the firewall on). DNS servers are set directly in `docker-compose.yml`; with the firewall on the container's resolver is Clash.
- **Who runs as whom.** See Privilege Separation. Root processes: supervisord, the gate (`sync-service`), the backup and vault-sync jobs, cron, and the bridged commands. Root without `CAP_SYS_PTRACE` cannot read the `/proc/<pid>/environ` of Caddy and Clash either.
- **The audit trail records claims, not proof, and not everything.** Logins (right, wrong, throttled), logouts, Cloudflare Access sign-ins, WebSocket handshakes refused for their Origin, every call that reaches the self-destruct endpoint while it is enabled, and egress status changes go to `/var/log/sdw/audit.jsonl` (root-only, rotated, on a volume that survives container re-creation) and to stdout. The client address comes from `CF-Connecting-IP` / `X-Forwarded-For`, which a caller reaching the origin directly can set, so it identifies the claimed source only; there is one master password and no user name. Wrong passwords and refused destruct calls are capped at 30 lines a minute (the rest are counted in one `audit.suppressed` line) so a flood cannot rotate the log away; a successful login, a logout and a destruct that fires are never dropped. The log is on the container's own disk, outside the vault: anyone who can read the container as root can read it, and `docker compose down -v` deletes it. The passwords never appear in it.
- **Logins are rate limited, not locked out.** 10 attempts a minute per claimed address and 60 across all addresses; the 11th gets `429` before any password is checked, even if it is the right one. A flood of forged addresses can therefore keep new logins out for the rest of a minute. Existing sessions and Cloudflare Access sign-ins are unaffected. The master password is also the vault passphrase, so a weak one remains the weak point: use a long one.
- **Egress state is observed and reported, never assumed.** At start-up the proxy is brought up and probed. The result is `confirmed`, `degraded` (proxy up, probe failed) or `down` (proxy not listening). A non-confirmed result does **not** stop the workspace; it is shown in the start-up banner, in `doctor` (live), in `/var/run/egress-status`, and as `.notifications/egress-degraded.md` inside the vault once it is unlocked. Clash routes in rule mode with one rule to a group that starts with `REJECT`: a subscription with no usable node makes requests fail, it never makes them go direct (an empty group would otherwise fall back to DIRECT)
- **The vault passphrase is also the master password**, and it is not memory-only: it comes from `PASSWORD` (so it is in the container environment and in `.env`, unless given as `PASSWORD_FILE`), or is generated; a generated one is printed in the start-up banner (so it reaches the container log) and kept in `/var/lib/sdw/master-password`. Code in the workspace cannot read any of these, but anyone who can read the container filesystem as root, its environment or its logs can unlock the vault. A design to make the vault key memory-only and hardware-rooted (TPM2 seal / KMS, plus splitting the login credential from the vault key, plus a microVM) is in `deploy/docs/design-memory-only-secrets.md` — design only, not implemented, because this box has no container-visible TPM2 and colima cannot nest a microVM; the hardware-gated check is `src/tests/smoke/manual/tpm-seal-verify.sh`
- **Secrets can be kept out of the environment, but are not by default.** Any of `PASSWORD`, `CLASH_SUBSCRIPTION_URL`, `VAULT_GIT_REPO`, `RESTIC_PASSWORD`, `AWS_ACCESS_KEY_ID`, `AWS_SECRET_ACCESS_KEY`, `PENTEST_VAULT_PASSWORD` and `CROC_PASS` can be given as `<NAME>_FILE=/run/secrets/...` instead (`docker-compose.secrets.yml`, `make secrets-init`); then only the path is in `docker inspect` and in every process's `/proc/<pid>/environ`. A value left in `.env` is still used, and is inherited by every root program (the workload never gets it). What stays regardless: a Compose file secret is a bind mount of a host file (not a tmpfs), and it is still the vault passphrase.
- **A generated password does not outlive its container.** It sits only in that container's `/var/lib/sdw` and log, so recreating the container with `PASSWORD` empty makes a new one and the vault made under the old one cannot be opened without it (reproduced: a restart keeps it, `docker rm` + start does not). Availability trade-off of keeping the passphrase out of `.env`; set `PASSWORD` or keep the printed one
- **The Clash subscription URL** is a credential too; it lives in `.env` and, rendered into Clash's configuration (0600, `clash`), in the `clash-config` volume, outside the vault
- **The `VAULT_GIT_REPO` URL, access token included, is stored in `.git/config` of the cipher directory**, on the same volume as the ciphertext and outside the vault (root-only). Whoever can read that volume gets the token as well as the ciphertext, and with it can push to or delete the replicated repository. Use a token limited to that one repository
- **On Linux hosts with AppArmor the vault cannot mount under Docker's default profile**: it forbids `mount(2)`, so gocryptfs fails with `fusermount3: mount failed: Permission denied` (reproduced on Ubuntu 24.04 in a VM; Docker Desktop has no AppArmor). The fix is `docker-compose.apparmor.yml` (`apparmor:unconfined`), opt-in because it removes the last confinement layer the container still has; with `CAP_SYS_ADMIN` and `seccomp:unconfined` already set, the container then relies on little beyond namespaces and capabilities. A tighter fix would be a custom AppArmor profile that only allows `mount` of `fuse.gocryptfs`; none is shipped
- **The restic backup is not part of the vault's protection.** It copies the plaintext workspace to the configured repository, protected only by `RESTIC_PASSWORD`. Self-destruct never deletes that repository (it can delete the `VAULT_GIT_REPO` remote with `--remote`, and only that). Anyone holding the repository and `RESTIC_PASSWORD` has the workspace
- **A forced `lock-vault` (lazy unmount) does not cut off processes that already have files open**: the mount disappears from the path, but code-server, a shell with its working directory in the vault or a running tool keep using what they hold until they exit, and the gocryptfs process (with the key in memory) lives as long as they do. Restart the container to be certain
- **A process listening on a unix socket inside the vault pins the mount without being an open file**, so `fuser` (which the unmount escalation relies on) neither shows nor kills it. The desktop session used to start such a process, an `ssh-agent` whose socket sat in the session's HOME inside the vault; it survived "stopping" the desktop, one more per start, and made every graceful `lock-vault` fail (measured: the unmount refused for 20 s with no process holding a file). The image now turns the session's ssh-agent / gpg-agent off. A socket you create yourself in the vault has the same effect: `grep ' /workspace' /proc/net/unix` lists them
- **The desktops have no authentication of their own; they rely on the ingress auth gate.** KasmVNC runs with `-DisableBasicAuth -SecurityTypes None`, and the Selkies server on `127.0.0.1:6080` runs with its Basic auth switched off (Selkies 2.x turns it on by default). Besides the stream it serves a small API (a screenshot, the session list, a file manager for uploads and downloads in `/workspace/.desktop/Desktop`), all of it as `dev`, so the same reach the desktop's own terminal has. The session cookie is required to reach `/vnc/`, `/websockify` and everything under `/desktop/` (Invariant 5), and a cross-site Origin is refused. Do not run the desktops with the gate disabled or bypassed. Residual: the gate protects the ingress, not the `127.0.0.1` loopback inside the container — a process already in the container, `dev` included, can reach `:6080` and the VNC port directly, which is the desktop it already owns
- **The pentest vault is mounted with `allow_other`**, so any user of the container can reach the mounted root file system, subject to its file modes (tor runs there as `debian-tor`, apt downloads as `_apt`). This is a difference from the workspace vault, which only `dev` can enter, and `dev` can: its pentest ciphertext is not readable (0700) but a mounted pentest rootfs is, while it is unlocked. The plugin's commands need `SYS_CHROOT` and `MKNOD`, which the default compose file does not grant (`docker-compose.pentest.yml` adds them with `NET_RAW`)
- **An SSH `VAULT_GIT_REPO` trusts the server's host key the first time it is seen** (`StrictHostKeyChecking=accept-new`) and pins it in `~/.ssh/known_hosts` inside the vault; a key that changes later is refused (checked against a real sshd). The alternative, refusing unknown hosts, made the unattended job fail with "Host key verification failed" until someone accepted the key by hand, and its only message was "push failed". A first connection to a server an attacker is impersonating would hand that attacker the ciphertext and the right to refuse updates, not the key or the data
- **Nothing restarts an unhealthy workspace.** The image has a health check and Docker reports it, but Docker does not restart a container for being unhealthy; `restart: unless-stopped` only covers the process exiting. A hung Caddy or gate is visible in `docker ps` and `doctor`, and `docker restart` is the repair
- **There is no memory limit by default** (`MEMORY_LIMIT` unset): a runaway process can take the host's memory. Set it per instance (`MEMORY_LIMIT=8g`); a limit under about 1 GiB can make the unlock itself fail, because gocryptfs needs 256 MiB for a moment with the stronger scrypt cost

## Self-Destruct Attack Surface

### 机制

| 触发方式 | 认证 | 攻击面 |
|----------|------|--------|
| CLI (`self-destruct`) | 容器 exec 权限 (Docker socket)，且必须是 root：`dev` 用户会被拒绝并提示用 `docker exec` | 与 `docker exec` 等价 |
| API (`POST /sync/api/destruct`) | bcrypt-hashed destruct passphrase | 暴力破解 |
| SPA (`#emergency`) | 同 API | 同 API (前端仅为 UI) |

### 防御措施

| 威胁 | 缓解 |
|------|------|
| 暴力破解 destruct passphrase | 速率限制: 3 次/分钟/IP; bcrypt cost=12 (~250ms/verify) |
| 信息泄露 (passphrase 正确性) | 所有失败统一返回 404 (无区分) |
| 重放攻击 | 无状态 API，但 bcrypt 验证本身是幂等的；销毁后 inert 模式阻止重复执行 |
| 未授权远程触发 | Cloudflare Access OAuth 前置认证 + destruct passphrase 双因素 |
| 宿主机残留 | host-watcher 检测 marker → `destroy.sh --paranoid` (清理 Docker 缓存、shell 历史、DNS) |
| 密钥派生弱点 | HKDF-SHA256 with domain-separated salt ("destruct-key-v1") |
| 容器重启后恢复 | `completed` marker 持久化在 named volume → entrypoint 检测 → inert mode |
| 挂载被占用 (EBUSY) | 逐级升级：`fusermount -u` → 杀掉占用挂载点的进程 → 杀掉占用整个文件系统的进程 → lazy 卸载。**绝不杀调用者自己及其祖先进程**（终端里运行 `self-destruct` 时，杀掉 shell 会挂断终端并带走调用者，密钥来不及销毁）；调用者先离开挂载点（否则 lazy 卸载后 `getcwd` 失败，后续每一步都报 ENOENT）。两种情形都在容器里复现并修复，见 `src/rust/infra/src/gocryptfs.rs` |

### 不可防御场景

- 已配置的 restic 备份仓库不会被删除，仓库里是明文工作区，只靠 `RESTIC_PASSWORD` 保护；自毁只会在 `--remote` 且有 token 时删除 `VAULT_GIT_REPO`
- 攻击者已知 vault passphrase → 可推导 destruct passphrase (设计如此: 同一信任根)
- 物理访问 + 已开机 + vault 已解锁 → 可直接读取明文 (与无 self-destruct 时相同)
- Docker socket 暴露 → 可 exec 任意命令 (与无 self-destruct 时相同)
- **host-watcher 的容器→宿主升级**：可选安装的 host-watcher 仅凭 destruct-state 卷里出现 `completed` 标记，就在宿主上运行 `destroy.sh --force --paranoid --delete-project`（删项目目录、`~/.cloudflared` 凭据、刷 DNS、洗 shell history）。标记所在的 `/var/run/self-destruct` 现在只有 root 能写，所以工作区里的代码（以 `dev` 运行，包括 code-server 被攻陷的情形）无法再诱发它；容器内取得 root 的攻击者仍可以——破坏而非窃取或执行。watcher 默认不安装（bootstrap 询问，默认否），只监视**它自己那个容器**的 destruct-state 卷；`destroy.sh` 的清理限定在该 compose 项目的卷，删除项目目录必须显式加 `--delete-project`，并有目标校验（拒绝空/`/`/`$HOME`/非项目目录）。不信任容器不被攻陷时，不要安装它
